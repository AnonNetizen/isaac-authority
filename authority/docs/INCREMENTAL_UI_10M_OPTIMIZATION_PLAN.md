# 1000 万内的字段索引与证据优化

保留旧模组源码、个人配置独立和主机奖励规则 `personal-settings-authority-hud-v1`。只运行命令行研究环境，工作上限固定 10,000,000。历史 DLL、清单和失败记录先做可校验快照；每个候选使用独立输出目录。

## 第一步：字段索引增量维护

现在每次键的存在性变化都会丢弃整张表的索引，再扫描、排序全部哈希节点。EID 1000 万失败账本中，字段排序约占 356 万。

改为维护按规范键排序的索引，逐键插入或删除；普通值更新保留槽位。数组仍按原整数顺序遍历，包括 nil 槽；哈希仍按旧规范键顺序遍历，保持来源和消费事件不变。表扩容使所有地址失效，执行明确的重建。Lua 在不扩容时搬移碰撞节点，也必须更新旧键的槽位，不能假定只有扩容会使指针改变。索引查找、实际比较、分配、复制和地址维护全部入账。

先用冻结旧 23 项和新增的碰撞、删除重插、混合键、nil 数组及重定向写入测试，与参考 Lua、全量标记和逐值 oracle 对照；检查完整生产者图、对象版本和消费事件。通过后再测真实初始化的两次运行。节约的账本和后移的失败位置不等于功能验收通过。

## 第二步：有界、可完整展开的证据表示

MCM 65,536 条证据中约 90% 是叶缓存读取。先统计重复描述和变化的消费位置、epoch、逻辑访问起点。候选把稳定描述与每次使用分开存储，每次消费仍保留自己的逻辑编号、位置、状态时点和动态参数；完整展开必须逐事件等于未压缩格式，不能省略消费或任意重新编号。

旧 65,536 条逻辑事件限制保留为历史对照。压缩候选须明确报告新的容量模型：65,536 个描述、65,536 个位置，以及独立的存储字节限制；每个逻辑消费至少收费一次，数量同时受固定 1000 万工作量约束。不能声称原逻辑条数限制未改变，也不能只把数组分页就当作压缩成功。未知描述、错误引用、存储超限或完整展开不一致都拒绝。

建立描述、查询、逐次使用及报告展开都收费。完成事件引用仍指向更早的逻辑事件；运行时检查引用类型、对象及版本，拒绝引用未完成或未来记录。缓存的资源、对象身份及激活上下文不删除。先跑有限模型的全量展开对照和容量负例，再运行冻结真实源码。

## 第三步：复测与阶段结论

各机制按顺序独立验收。两次命令行运行比较配置、普通结果、来源、完整生产者图和展开证据；真实失败前缀或费用不稳定原样报告。检查超限不能继续执行、未知 API 和结构限制仍拒绝。最后核对冻结模组/SDK/资源及存档配置基线，记录二进制与清单哈希。

初始化尚未全部通过时，绘制捕获、真实菜单导航、游戏世界、通信和解锁保持未开始。本轮不要求操作游戏或第二台电脑。发生机制性失败时保留候选和首个入口，按证据修复；不能以安全拒绝冒充兼容通过。
