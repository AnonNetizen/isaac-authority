# 执行与审计解耦：分步重构

保持：Windows x86、每上下文 10,000,000 工作单位、旧模组源码不变、个人配置独立、奖励及其显示跟随主机。只通过命令行测试，不启动游戏。

## 1. 缓存证明与历史审计分离（本次先验收）

- 新建独立候选 `ia-lua533-execution-audit-1`，保留 Compact DLL、源码、清单和报告。
- 完成一次遍历后，在对应活跃 memo 中保存完成时根版本和原证据编号。缓存复用只读取该证明与当前版本，不重新解码历史文件。
- 证据描述、使用记录和精确查重索引采用有界的内存表示；审计接收同样的逻辑记录。禁止用哈希相同代替内容相等，禁止忽略保存/写入失败。
- 证明只在证据成功追加之后发布。无效或不完整证明拒绝执行。
- 统计 root / leaf / aggregate 命中范围内的审计读取次数，必须为零。对照旧版返回值、来源、变量版本和完整逻辑证据。
- 内存仍受 DLL 512 MiB / 子进程 1 GiB 保护；证据编码限额 64 MiB、描述数和所有既有逻辑限制不放宽。

阶段边界：第一步不宣称整个执行已与审计解耦。值图当前仍有历史文件读取，后续必须单独消除，不能把全部历史节点搬回无界内存。

## 2. 活跃值图与审计输出分离

- 根据 Lua 根、host pins、活跃双视图、序列化和恢复需求保留运行必需的紧凑节点；历史取证单向输出。
- 根清单还必须包含活跃对象的字段版本、结构与对象来源版本，以及控制条件。现有回收器只证明部分侧表可以回收，不能据此直接释放全部历史节点载荷。
- 普通执行不得从审计恢复节点；缺失活跃生产者应拒绝。离线校验和显式诊断独立进行。
- 有界批量输出；写失败或空间不足阻止提交，不悄悄丢证据。
- 验证跨帧引用、回收、恢复、重复消息、审计故障及内存增长。

## 3. 字段和 upvalue 的失效范围

- 先区分全对象遍历证明与字段消费证明。全对象查询确实依赖全部字段，不能直接取消其失效。
- 字段消费记录精确读集合、结构依赖和实际 upvalue 版本；无关字段修改不使该消费失效。
- 验证相关/无关字段、缺失键、删除、布局变化、别名、脱离父对象、闭包共享 upvalue、join 和栈迁移。检查值和来源，不只检查命中次数。

## 4. 短基准与出口

- 每案例最多 5 秒，整批最多 90 秒；始终执行 10M 工作量拒绝。构建时间单独记录。
- 使用小规模递增数据、root/leaf 命中、修改后重算、别名、闭包、失败及预算边界；分别记录执行和诊断的耗时及读取次数。
- 对照旧 Compact 和官方 Lua，保留必要结果；重复审计经哈希确认后删除，不做 ZIP/解压副本。
- 先通过第一步，再进入第二步；随后才收窄失效范围。完整初始化和真实 MCM/EID 菜单不作为本次短基准入口。

测量结论须区分：零缓存命中回读、整个执行零回读、功能兼容、性能改善、完整重构通过。它们不能互相代替。

## 首轮短测试发现与判定修正

`execution-audit-step1-v1` 保留首轮失败：循环共享叶对象的功能、完整证明和审计字节均重复一致，但两次工作计数不完全相同。差异来自原有字段索引的内部树比较及 oracle 排序，受 Lua 哈希布局影响；对照旧版也有计数变化。这不是缓存结果改变。

v2 清单保留原 Lua 文件和功能预期，明确分开报告：功能/证据重复一致、每次工作计数合法、工作计数是否完全相同。前两项是本步缓存解耦的验收要求；第三项保持诊断，差异逐类列出。不能将这一修正称为已解决字段索引计数稳定性。
