# 追踪运行时成本复核

本轮停止全量 x64 测量，完整 EID/组合初始化的总工作量仍未测得。停止原因是现有实现持续保留大量记录，已经表现出无法直接用于游戏运行的成本；继续提高容量只能推迟触顶。正式 1000 万上限、旧模组源码、个人配置及奖励规则未改变。

## 实际证据

此前 x86 EID 英文执行到 193,247 条被追踪 VM 指令时，已经生成 14,928,656 个缓存证据使用记录、89,233 个描述及 446,758 个值图节点，编码证据接近 1.5 GiB，然后因容量拒绝。约 77 个缓存证据事件对应一条已执行指令；这是部分初始化的实际放大，不是完整运行的平均值。数据来源为 `reports/ui-incremental-walk-completion-sizing-500m-1536mib.json`。

另一个 x86 组合英文失败前的 447,428,098 工作单位中，来源合并占 60,256,865、证据描述字节比较占 59,727,442、对象身份占 52,497,975、字段关系占 41,202,306、递归标记占 36,052,981、证据使用占 35,875,972。成本分散在传播和证据维护，不能只归咎于字体、EID 本身或者一个容量常数。

## 源码中的成本机制

- `incremental.inc` 的 `inc_touch` 为字段计版本，但 `inc_dirty_walk` 仍使对象及可达父对象的根版本失效。`aggregate` 只缓存完整根的聚合，根版本改变后重新枚举可达内容。因此当前缓存不等于按实际读取字段进行增量求值。
- `inc_link` 保留已经失效的反向父边以避免漏失效。这样做保守，但在有覆盖和别名的长期上下文中会扩大后续失效传播范围。安全性理由不能代替成本控制。
- `ia_trace_enter` 对原生函数的每个实参做递归来源聚合，`ia_trace_leave` 对返回值递归标记。这一通用兜底会把大型表或闭包的内容带入操作；已经登记的简单原生操作也没有充分使用各自的字段读取/写入契约。
- `IncEvidenceStore::append` 将描述 JSON 序列化为字符串，通过有序字典逐块比较，并同时保留描述与字典字符串。叶检查点还包含字段版本表。共享描述降低了重复存储，却没有消除版本变化产生的大量新描述及其构建/比较成本。
- 值图节点和逻辑证据按上下文保留，尚未建立由当前可观察状态、未解析分支、持久配置元数据及恢复检查点定义的安全回收机制。精简报告复制没有解决底层常驻记录增长。

这些是源码可确认的结构性机制。尚未取得当前 x64 加载过程的逐操作现场剖析，不能声称已经精确归因每一字节或证明某一次具体原生调用是最大热点。

## 调整方向与验证顺序

1. 先用小型压力程序分别测量表扩容/覆盖、原生迭代器、闭包和别名传播、证据描述生成。对照未修改 Lua 的结果、原全量来源、值图证据与错误；观察 N、2N、4N 的实际工作量和常驻内存，定位放大，不立即再跑完整 EID。
2. 字段/upvalue 保留版本身份，已登记原生函数按真实读取和副作用传播；把按字段读取与“显式消费整个结构”的用途分开。未知函数继续拒绝，不能为降低费用把未知当作无依赖。涉及别名、循环和控制依赖的变更须先通过原反例。
3. 将运行所需依赖与诊断审计表示分开。常驻记录使用有类型的 ID 和明确操作数，避免为每个事件构造大 JSON；诊断按需导出或无损写出。新的工作量账本要照计实际索引、传播、证据和导出操作，不删收费来伪造通过。
4. 定义图和旧版本的存活根、失效边维护、循环回收和检查点保留规则。已接受跨帧配置与奖励引用、尚未解析的分支和恢复历史不能被丢弃；先证明回收后查询/投影/恢复一致，再限制常驻记录。
5. 小压力程序和旧反例证明正确且成本改善后，才在正式 1000 万上限内重新验收真实初始化，再推进绘制捕获和菜单导航。无法在上限内完成仍算门槛失败。

字段/upvalue 版本和明确原生契约仍是可研究的底座；当前“完整递归传播 + 全历史常驻审计”的实现没有证明实际游戏可用。这个结论不改变旧模组无需逐个修改、个人配置独立、奖励跟随主机的目标，也不保证调整后必然满足任意旧模组。
