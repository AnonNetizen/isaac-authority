# 值对象压力与增量证明：十次修改短测通过

本轮仍是独立 Windows x86 Lua 5.3.3 金币模型，ABI 为
`ia-lua533-settings-value-1`。没有附加或启动游戏，没有修改个人存档。
旧模组源码不改、个人配置独立、奖励跟随主机的要求保留。
真实游戏渲染和联机仍未通过。

## 本轮改动

新增 `native_value_pressure=true` 研究策略。登记达到高水位 768 后，在已提交
回调之外进行有界堆普查，预先记账，再调用固定 Lua 源码的 emergency 收集
路径。该路径跳过 finalizer 执行，保留待执行队列；弱引用清除后释放 C++ 值
对象登记。没有把 1024 登记上限改大，也没有运行第二次世界逻辑。

用户停止 Lua GC 时，压力请求直接返回。当前策略要求 Vector/Color/KColor
的原生 finalizer 保持登记契约；初始化身份不符或后续改写 `__gc` 均明确拒绝。
因此不能宣称支持任意原生 metatable/finalizer 改造。普通 Lua 表的 finalizer
没有删除：测试证明压力路径内计数保持 0，后续正常 GC 后变为 1，再次 GC
仍为 1。压力处理后注入失败会重建已接受历史并恢复此前状态。

来源指纹改为只对持久字段和 upvalue 当前引用的新增依赖做增量预计算。
同一节点仍使用原指纹公式、完整生产者关系和原 64 层递归保护；没有截断
因果链。先按不复用的来源编号检查生产者顺序，再缓存已证明结果，使之后
的消费可以引用前帧证明。未知来源仍不能因缓存而变成合法结果。

第一版曾给全部临时界面节点计算指纹，十次短测超过 5 秒。该失败保留于
`native-pressure-stress-v1`；当前仅处理持久存储的新增依赖。十次用例中个人
上下文仅计算 88 份指纹、检查 89 个仍保留的值，未恢复全量初始化追踪。

## 无损报告共享

执行继续使用活跃值图，审计文件不参与缓存命中。十次逻辑完成后，曾因重复
绘制帧和精灵状态超过 2 MiB 输出配额，失败报告保留于
`native-pressure-stress-v2`。

新增可选 `shared_draw_audit=true`：按实际 JSON 内容共享绘制帧和捕获状态，
同时保存序列化字节的 SHA256。C++ 在发送前完整解码并检查 JSON 相等；
Python 验证哈希、引用类型、范围和配额，再恢复原始绘制命令。共享与不共享
的同一真实 MCM 用例，配置、绘制帧、设置证明与权威结果逐项相同。

传输配额仍为 2 MiB；逻辑报告和客户端展开另有 16 MiB 上限。字典最多
4096 个状态、256 个帧，解码最多 512 个步骤。异常引用、非有限数、哈希
损坏和膨胀攻击会拒绝。9 项解码测试通过。报告仍可选择只导出来源图摘要，
这不等于导出了完整的历史依赖图。

最终十次用例为约 3.815 / 3.790 秒、4424526 / 4424890 工作单位，结束私有
提交约 45.1 MiB。两套个人上下文都进行了一次压力收集，登记从 814 降到
88，各释放 726 份登记；来源图结束约 1050 / 1060 节点。
这些是整份命令行用例的耗时和结束内存，不是游戏帧延迟或峰值曲线。

正式限制继续为 1000 万工作单位、5 秒子进程超时、1 GiB Job。来源图仍是
4096 节点/1 MiB。GC 的工作量采用有界普查和预付遍历额度，属于混合记账，
并非逐条统计 C 指令；实际墙钟时间另由子进程超时约束。
