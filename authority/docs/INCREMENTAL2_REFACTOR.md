# 增量追踪架构重构

保留正式 x86 1000 万上限、旧模组源码、个人设置独立及 `personal-settings-authority-hud-v1`。新候选位于 `incremental2_ui_runtime`，ABI 为 `ia-lua533-slice3-ui-incremental-2`，只由独立命令行宿主加载。现有游戏入口继续拒绝该 ABI。

按门槛顺序推进，不再先用完整 EID 消耗内存：

1. 原生字段契约与实际写入：先消除 `table.insert/remove` 对整表的递归实参收集、返回标记和合成字段重写；保留每次实际字段写入的值版本、控制来源和调用身份。区分字段成员变化与内存布局变化，按父字段引用计数移除失效反向边。带元表的操作及尚未验证的排序保留明确的保守旧实现，不声称已优化。未知原生函数继续拒绝。
2. 紧凑依赖图：把运行时 JSON 图改为有类型的生产者、操作数、字段及 upvalue 版本，验证别名、闭包、分支、跨帧引用和个人/主机双视图后再替换旧表示。
3. 完整审计与存活根：完整审计分块落盘，运行所需引用与历史证据分开；补齐可达根和循环回收。跟踪器管理内存 512 MiB、进程私有提交 1 GiB、审计缓冲 8 MiB、每例磁盘 4 GiB；编码、I/O、索引和回收计入账本，不能降低收费来冒充优化。
4. 运行全部原反例与真实 MCM/EID 中英文初始化。需要兼容的案例被拒绝仍算门槛失败；通过后才推进绘制和菜单输入。

第一门槛仍使用受限的旧 JSON 图和证据存储，尚未实现第二、三门槛，因此不能把小程序通过写成整个新架构通过。每个案例使用独立 Lua 上下文；普通值和错误对照官方未修改 Lua，精确字段来源按冻结预期检查。N=256/512/1024 检查实际工作量、图节点、字段写入、时间与进程私有提交；局部追加/覆盖增量的倍增比要求不超过 2.5。原生中间插入/删除本身需要移动元素，不将其本来就有的线性移动次数算成追踪器缺陷。

旧 DLL、源码、清单和失败报告保持原位。只使用一个新的构建目录与一个汇总报告目录；完整案例证据压缩保存，不保留重复解压树，不启动游戏或写入个人存档。

## 第一门槛结果（2026-10-14）

`ui_incremental2_stage1_v7.json` 的 24 项与 `ui_incremental2_legacy_oracle_v2.json` 的 27 项均完成：49 项功能通过，2 项安全拒绝按预期复现。后者包括历史尾调用上下文限制，仍属于不支持，不能算兼容。每例新候选运行两次，完整生产者图、字段/upvalue 证据、版本和来源一致；返回值、false/nil、原始字符串字节及普通 Lua 错误对照未修改 Lua。独立的无缓存全遍历 DLL 检查来源传播，两个对照使用相同原生契约，故它验证缓存与传播的一致性，不证明原作者意图。

| 小模型 | N=256 工作单位 | N=512 | N=1024 | 增量倍增比 |
|---|---:|---:|---:|---:|
| 追加 | 120375 | 242122 | 490885 | 2.043 |
| 覆盖 | 134708 | 270930 | 547842 | 2.033 |
| 读取 | 69955 | 138011 | 274165 | 2.001 |

N=1024 时进程私有提交分别约 86.1、100.8、64.1 MiB，包含旧 JSON 图及完整诊断导出。增长检查只覆盖冻结的规模范围，不证明所有程序均为线性。

同一追加 256 项案例，旧候选工作量为 7798596，新候选为 120375；旧候选私有提交约 198.1 MiB，新候选约 22.2 MiB。旧候选仅导出摘要，也没有新候选的诊断编码/I/O 计费；这些是该模型下的成本观测，不能解释为相同端到端负载的游戏加速倍数。正式 1000 万上限不变，新候选的来源证明、反向边更新、证据及诊断导出仍收费。

实际修正包括：

- `table.insert/remove`、`rawget/rawset/rawlen` 采用登记的字段契约，依据真实 C 函数身份识别；捕获 `lua_seti` 的实际写入，去掉整表合成重写。缓存函数仍走同一契约。
- 按父字段引用计数断开失效反向边；仍有别名时保留依赖。区分字段成员版本、字段值版本和布局版本；数组向哈希区搬迁不能冒充逻辑赋值。
- 字段值是否为 nil 影响成员存在性时保留其来源。只有已登记生产者和控制依赖能证明存在性固定时才省去无关值依赖；未知输入继续保守追踪，不能当作纯界面。
- 显式对象来源、调用函数来源、结构查询和字段读写均留有生产者证据。缓存/无缓存来源与图证据必须一致。
- 元表将写入转交给函数或另一张表时，代理表不提交成员/字段版本；真正目标单独捕获。只有 `__index`、没有 `__newindex` 的表仍正常提交写入。数组字面量的 `SETLIST` 也走同一来源入口，避免漏掉可空值造成的结构依赖。

最初沿用历史过度污染输出的对照有 3 项失败，报告保留在 `reports/ui-incremental2-stage1/legacy-oracle`：元表代理的未写字段、循环重绑定后的无关字段、布局重绑定后的无关兄弟字段。新清单保留相同源码和普通 Lua 结果，改用独立无缓存来源对照，并保留历史来源差异作为诊断；没有把旧失败报告覆盖为通过。

47 项通过后的收尾审计又发现可空值经过元表代理、数组字面量时的结构来源缺口。失败记录分别保存在 `metatable-audit-v1`、`metatable-audit-v2`，对应 DLL 哈希及第二次审计的二进制保留；初版研究包及其哈希仍保留。最终 v7 清单原样纳入这些反例，完整 51 项再次执行，不以旧 47 项通过代替新增功能验收。

旧候选源码、DLL、静态库及 31 个存档/配置原件和备份的前后哈希一致。旧 13/31/24/42/56 项完整模式清单本阶段没有重跑，仅做保护校验；它们在第 4 门槛回归。

## 命令行复现

在原工作区执行第一门槛：

```powershell
python -B authority/tools/run_incremental2.py --output authority/reports/ui-incremental2-stage1/new-native-run
python -B authority/tools/run_incremental2.py --manifest authority/research/ui_incremental2_legacy_oracle_v2.json --output authority/reports/ui-incremental2-stage1/new-legacy-run
```

输出目录必须不存在。每个进程由 Windows Job Object 限制到 1 GiB 私有提交；案例诊断上限 64 MiB、超时 90 秒。证据通过宿主流式压缩归档，但运行时仍先构造旧 JSON 图，**尚不属于运行时审计落盘**。512 MiB 跟踪器配额、紧凑图和回收仍未实现，报告对应标志保持 false。

研究包解压到临时目录后，从包根执行以下命令；结果放在解压树外，完成后删除解压树，仅保留结果。复现入口不读取安装目录、游戏存档或基线备份。

```powershell
python -B authority/tools/reproduce_incremental2.py --bundle . --output D:/Coding/ISAAC/authority/reports/ui-incremental2-stage1/new-replay
```

该入口逐文件校验包内容，并重新执行全部 51 项，与冻结的生产者、字段/upvalue 证据和结果比较。普通参考及无缓存对照的原始证据也在包内。若需重编译，包内包含独立 CMake 工程、全部 Lua 派生源码、固定官方源码和所需旧静态库，使用 Windows x86 Release；不替换游戏 DLL。

下一门槛是紧凑有类型依赖图：共享字段/upvalue 的版本身份，分开运行所需状态和历史证据，先对照本门槛 51 项，再接审计落盘及存活根回收。真实 MCM/EID 尚未重新运行，绘制捕获、菜单导航和主机权威联机仍未通过。
