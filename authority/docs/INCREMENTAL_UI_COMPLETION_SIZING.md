# 初始化完整工作量的临时测量

2026-10-11，只运行独立 Windows x86 命令行研究环境。正式 10,000,000 工作量版本的源码、DLL 和容量限制保持不变；不启动游戏、不写个人配置或存档。

为了测量完整初始化的工作量，临时 DLL 的工作量截止线为 100,000,000，编码证据容量为 512 MiB，测量进程允许使用较大的 x86 地址空间。其余执行追踪、费用规则、框架源码、输入、资源和契约检查沿用当前版本。单次依赖遍历的 16,384 次访问和 24 层深度等结构边界保持。本次不是正式预算升级，也不是兼容验收。

每项执行一次，中英文各测一次；Lua 哈希布局等因素可能使工作量变化，不能把一次测量当作保证上界。工作量覆盖 J460 枚举、冻结模组加载及现有契约检查；读取被动计数器不执行 Lua 或重置预算。未执行最后的完整依赖报告导出，不能称为整个正式验收流程已经完成。数字不是每帧成本或 Lua 指令数。

EID 和组合加载的首次拒绝均为 `authority-load-entry:1: Trace marking budget exceeded`，未耗尽临时 1 亿工作量。因此表中的值是失败前已用工作量，不能作为跑完的总量。该错误同时覆盖逻辑访问及深度边界，本次没有进一步区分或放宽这两个边界。EID 英文失败前的编码证据已占 155,052,410 字节，超过正式 64 MiB 容量；完整跑完的容量需求也尚未知。

MCM 英文完整现有检查中的较大费用包括：活跃 upvalue 搜索 4,770,357、证据比较字节块 4,494,113、证据描述比较 3,004,801、对象身份操作 2,885,779、来源合并 2,703,858。不能只减少收费来使其低于正式上限，后续优化仍需证明省去的是实际重复工作。

所有工作量均与费用分类之和一致。MCM 的契约观察值均符合冻结预期；六项原模组文件哈希和主 Lua 栈恢复检查通过。最终重新核对正式运行时源码、借用的原生静态库、正式 DLL 和 31 个个人存档及配置文件，均未变化；143 个模组 Lua、2 个 J460 脚本和 64 个本地资源校验保持。个人配置独立、主机奖励投影规则保留；本次仅初始化测量，不新增奖励、HUD 或菜单导航验收结论。

临时二进制、派生源码和逐项原始输出位于 `%TEMP%/isaac-init-sizing-20261011`。持久测量报告与全部费用分类、派生信息、哈希在 `authority/reports/ui-incremental-completion-sizing.json`；入口为 `authority/tools/probe_incremental_completion.py`。重新测量应创建新的临时目录，不能覆盖既有记录。准备完成后用其独立 CMake 工程编译 Win32 Release，再执行入口的 `run` 和 `finalize` 阶段。

结论：MCM 当前初始化及现有契约检查约需 3,246 万工作单位，是正式上限的约 3.25 倍；EID 与组合加载只能获得失败前下限，增加总工作量不能解决先触发的单次遍历限制。正式候选仍未通过真实初始化门槛。
