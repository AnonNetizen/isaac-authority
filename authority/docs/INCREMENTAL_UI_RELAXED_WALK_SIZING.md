# 临时放宽单次依赖遍历的测量

本轮沿用冻结的 MCM/EID、J460 枚举、资源、输入、契约和 `personal-settings-authority-hud-v1`。只运行独立 Windows x86 命令行；正式 1000 万上限、正式源码和 DLL、个人存档及配置均不改。此处测量的是上下文初始化及现有契约检查，不是游戏帧耗时，也不代表兼容门槛通过。

单次逻辑访问从 16,384 临时提高到 262,144，递归深度从 24 提高到 256。缓存叶的逻辑访问、深度、证据操作数和相关来源/图查询的遍历边界一起调整；费用逐次照计，不删除记录或跳过未知操作。测量进程用 16 MiB 栈。旧边界程序原样执行，两项均返回预期的 1；正式版本仍保留旧拒绝预期。

先后测量：

| 临时版本 | 工作量截止线 | 编码证据容量 | 图节点上限 | 结果 |
| --- | ---: | ---: | ---: | --- |
| v2 | 1 亿 | 512 MiB | 262,144 | EID 中英文分别在 73,006,564 / 73,080,050 触达证据容量；组合加载均耗尽 1 亿 |
| v3 | 2.5 亿 | 1 GiB | 262,144 | EID 中英文在 134,610,166 / 136,606,095 触达图节点上限；组合加载在 123,635,966 / 123,609,745 触达同一上限 |

这些均是失败前已用工作量，不能当作完整跑完的总量。持久历史报告分别为 `reports/ui-incremental-walk-completion-sizing-100m-512mib.json` 和 `reports/ui-incremental-walk-completion-sizing-250m-1gib.json`。

下一临时版本将工作量截止线设为 5 亿、编码证据设为 1.5 GiB、稳定描述设为 131,072、图节点与消费记录设为 1,048,576。源码初始化和原有检查仍全部执行。

检查桥原本从完整追踪报告中只读取失败状态。临时测量提供精简检查输出，保留底层全部来源、图、对象版本和消费记录，以及原检查的全部工作量收费；只避免把所有记录复制成报告再解析。最终完整依赖报告导出仍不在本次测量范围内。两种输出必须在同一上下文对照收费，防止不同 Lua 哈希布局影响跨进程比较。早期跨进程的 walk 对照因字段索引比较存在 1 单位差异而未通过，其记录保留；不删除该费用。

独立入口：`tools/probe_incremental_walk_completion.py`。派生源码、限制变更、二进制哈希和检查证明均记录在各临时目录及报告中。临时 v1 准备脚本的模板计数核对失败，未用于实测；之后修正为分别核对标记和查询的缓存高度。v4 仅进行检查输出对照，未进入真实加载。

后续 x86 测量仍没有完成：v5 的 EID 英文在 334,280,093、中文在 344,132,774 工作单位触达 1.5 GiB 编码证据容量，两个组合案例未计为完成。报告保留于 `reports/ui-incremental-walk-completion-sizing-500m-1536mib.json`。

v6 临时把证据容量提高到 2 GiB。EID 英文与组合英文均先报 `bad allocation`，随后进程以 `0xC0000409` 退出。组合案例可以从已完整序列化的前缀恢复 447,428,098 工作单位；EID 前缀不完整，不能给出完整费用。两者都不算通过。EID 观察到的峰值工作集为 3,828,715,520 字节，接近 x86 可用地址空间。此版本的旧边界完整报告仍有描述容量标签未更新的元数据缺陷，实际临时头文件及派生记录为 131,072；不能把标签视为实际容量。原始记录保留在临时目录，汇总为 `reports/ui-incremental-walk-completion-sizing-500m-2048mib.json`。

在用户明确选择独立 64 位估算之后，转入 `tools/probe_incremental_x64_completion.py`。64 位结果单独记录，不能替代正式 Windows x86 验收。
